# V0.3 落地范围

V0.3 补齐“知识问题能够持续被处理”的第一版闭环，重点不是新增更多目录，而是让 Review、来源修订和资料摄取进度真正进入统一知识变更过程。

## 已实现

### 1. Review 稳定身份与新证据重开

- 稳定 ID 由 `kind + scope_key + normalized title` 生成；
- 相同问题再次出现时复用同一 Review；
- 已 resolved/dismissed 的 Review 遇到新的 `evidence_version` 会自动 reopen；
- 保留历史解决记录和 reopen 原因；
- Review 物理记录位于 `changes/reviews/YYYY/MM/`；
- `index` 生成 Review 导航，不将 Review 当成 PR 审批状态。

该机制参考 llm_wiki review-store 的“内容稳定 ID + resolved 状态保留”设计，并增加团队范围、证据版本、历史与重开语义。

### 2. 来源稳定身份与修订影响

`refresh-source`：

- 保留原 `source_id`；
- 新内容 SHA 与旧版本比较；
- 旧内容归档到来源资料包的 `revisions/<hash>/`；
- 更新当前来源哈希与 revision 列表；
- 扫描正式知识中显式 `evidence.source_id` 依赖；
- 建立一个 CHG 和一个可重开的 Review；
- 将受影响 knowledge ID、旧/新来源版本与变更关联。

V0.3 只沿显式证据依赖定位影响，不宣称发现所有隐式语义依赖。

### 3. Text/Markdown 摄取分块与 review-progress

`intake-source` 为已登记来源建立：

- `manifest.json`；
- 分块 Markdown；
- `review-progress.yml`。

每个 chunk 必须处置为：

- `integrated`；
- `skipped`（必须给理由）；
- 或保持 `pending`。

只有所有 chunk 都得到处置，audit 才返回 complete。

该机制参考 project-wiki `ingest_document.py` / `review_progress.py` 的“不可跳过摄取覆盖账本”思想。V0.3 只支持 UTF-8 TXT/Markdown；PDF/DOCX 仍未接入。

## 测试覆盖

新增 V0.3 测试：

1. 相同 Review + 相同证据版本不会重复打开；
2. resolved Review 遇到新证据版本重新 open；
3. Text/Markdown intake 未处置完整时 audit 不通过；
4. 每个 chunk 完成 integrated/skipped 后才 complete；
5. 来源修订会定位显式依赖知识；
6. 来源修订会创建 CHG 与 Review；
7. 新来源版本会重开已解决 Review；
8. V0.1 / V0.2 旧测试继续回归。

## 明确未实现

- 自动修改正式知识正文；
- Review 的复杂阻塞范围和多人审批策略；
- 语义级隐式依赖传播；
- PDF/DOCX/图片 intake；
- project-wiki 完整 Schema/模板迁移；
- llm_wiki graph-insights / research-topic；
- LanceDB / embedding；
- MCP / UI；
- 自动 GitHub PR 审核/合并策略。

## 设计边界

- Review resolved 不等于 PR approved；
- 来源发生变化不等于已有知识一定错误；
- CHG 创建不等于正文已经修订；
- intake complete 只表示每个 chunk 已有处置，不表示所有结论都正确；
- 来源修订通过显式 evidence 追踪影响，隐式关系仍需 maintain/Agent 语义复核。
