# V0.6 落地范围：多来源归并、依赖影响、发布与采用闭环

V0.6 不新增新的顶层业务对象，而是把 V0.5 已有的 Candidate / Patch Plan / CHG / Work 补成完整的“多来源 → 修改 → 发布 → 采用”链路。

## 1. 多来源 Candidate 归并

新增 Candidate Batch 工作产物：

```
.knowledge/records/candidate-batches/BATCH-*.yml
```

Batch 要求参与 Candidate：

- proposed_id 一致；
- knowledge_type 一致；
- scope 一致；
- 每个 Candidate 均已有 Evidence Binding。

当前 Agent / 领域责任人显式提供 `merged_statement`，程序不自动总结业务含义。

Batch 会：

- 汇总所有 Candidate；
- 去重 Evidence；
- 保留 Evidence 的 supports / limits / contradicts / relevant 关系；
- 将 Evidence 重新绑定到一个 merged Candidate；
- 标记同一 Evidence 出现多种关系时的 conflict；
- merged Candidate 继续使用 V0.5 的 Patch Plan。

## 2. 显式依赖影响

正式影响传播只使用显式依赖：

```yaml
depends_on:
  - K-A
```

或：

```yaml
references:
  - id: K-A
    relation: depends_on
```

普通 `related`、向量相似、共同来源和 graph relevance 不视为必须复核的依赖。

V0.6 支持：

- 直接依赖；
- 反向 dependents；
- 传递影响；
- Knowledge；
- Analysis；
- 带 frontmatter depends_on 的 Overview/View。

Patch Apply 后自动计算显式依赖影响。

如果存在 dependents：

- 创建/复用 dependency Review；
- Review 挂到原 CHG；
- Patch Plan 保存 dependency_impact；
- CHG 保存 dependency_impact；
- Review 未处理前禁止正式 Publication。

## 3. Publication 不是 frontmatter 状态

新增：

```
.knowledge/records/publications/PUB-*.yml
```

Publication 必须满足：

1. CHG stage 为 proposed / ready；
2. CHG 的 Review 全部 resolved/dismissed；
3. 给出的 Git ref 可以解析为真实 commit；
4. 该 commit 中目标 Markdown 的字节哈希与当前知识正文完全一致。

Publication 记录：

- publication_id；
- knowledge_id；
- change_id；
- Git commit；
- path；
- content_sha256；
- adoption_requirement；
- published_at；
- effective_at。

adoption_requirement：

- notice；
- review-required；
- must-address。

这只是记录已发生的正式 Git 发布事实，不自动 push、merge 或修改保护分支。

## 4. Work 绑定 Publication

`prepare` 新增 consumer：

```
team-wiki prepare ... --consumer project-b
```

`adopt` 会读取目标 Knowledge 的最新 Publication。

仅当当前正文 hash 与该 Publication hash 一致时：

- publication_match = true；
- 记录 publication_id；
- 记录 published_ref；
- 记录 adoption_requirement。

如果当前工作树中的知识已经变化但尚未重新发布：

- publication_match = false；
- 不把它统计成正式发布版本的 adoption。

## 5. Adoption Record

Work finalize 后，将实际 adopted 且绑定 Publication 的部分写为共享记录：

```
.knowledge/records/adoptions/ADOPT-*.yml
```

记录：

- consumer_id；
- work_id；
- knowledge_id；
- publication_id；
- published_ref；
- used_for；
- outcome；
- evidence_ids。

`adoption-status` 按最新 Publication 查询：

- 哪些 consumer 已采用；
- 使用结果；
- 当前 consumer_count。

发布完成、采用完成、验证完成仍然分开。

## 7. 核心端到端链

```
Source A → Evidence → Candidate A ┐
                                  ├→ Batch → merged Candidate
Source B → Evidence → Candidate B ┘
                                  ↓
                         explicit comparison
                                  ↓
                           Patch Plan
                                  ↓
                            Patch Apply
                                  ↓
                        dependency impact
                                  ↓
                         dependency Review
                                  ↓
                         Review resolved
                                  ↓
                           Git commit
                                  ↓
                          Publication
                                  ↓
                        Project-B Work
                                  ↓
                           adopted
                                  ↓
                         outcome/evidence
                                  ↓
                         Adoption Record
```

## 8. 关键边界

- Batch 不自动决定 merged_statement；
- related/relevance 不当作强依赖；
- Patch Apply 不等于 publish；
- Publication 不修改 Git 历史，只核验已有 commit；
- open/blocked Review 会阻止 Publication；
- Work 读取未发布工作树内容时，不记为正式 Publication adoption；
- Adoption 说明使用了哪个版本，不自动证明知识正确；
- supported-in-scope 仍然只在该 Work 条件下成立。
