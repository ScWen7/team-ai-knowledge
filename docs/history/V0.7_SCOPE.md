# V0.7 落地范围：项目侧知识消费治理

V0.7 将团队知识库的 Publication 真正接入业务项目日常工作。核心目标不是“让项目能搜到团队知识”，而是让项目明确回答：

- 当前锁定的是哪个 Publication？
- 是否存在更新？
- 更新属于 notice / review-required / must-address 哪一类？
- 任务开始时是否允许继续使用旧版本？
- 发布前是否已经处理必须处理的更新？
- 任务中途知识锁发生变化时是否发生静默切换？
- 实际采用哪个 Publication，结果如何，是否已经回报团队知识库？

## 1. 项目 Profile

新增项目侧初始化：

```
team-wiki project-init <project-root>
  --project-id project-b
  --team-repository-id team-knowledge
  --knowledge-id K-A
  --knowledge-id K-B
```

项目共享配置：

```yaml
.knowledge/config.yml

version: 1
repository_id: project-b
profile: project
knowledge_sources:
  - repository_id: team-knowledge
    knowledge_ids:
      - K-A
      - K-B
```

V0.7 要求项目显式声明需要消费的 Knowledge ID。

**不由 Agent 自动推断并静默删除“看起来不适用”的规则。**

首版仅支持一个 team-knowledge source；多知识仓库联合消费后续再扩展。

## 2. Knowledge Lock

项目共享并提交：

```
.knowledge/knowledge.lock.yml
```

Lock 保存每条知识的精确 Publication：

- publication_id；
- published_ref；
- content_sha256；
- path；
- adoption_requirement；
- published_at；
- effective_at；
- change_id；
- locked_at。

Lock 是项目可复现知识基础，不是本地缓存。

本地 team-knowledge checkout 的绝对路径不写入共享配置；调用命令时显式提供已授权的 team root。

## 3. 初始锁定

```
team-wiki project-lock <project-root> <team-root>
```

只锁**已经生效**的最新 Publication。

如果最新 Publication 的 `effective_at` 在未来：

- 当前已有有效版本：继续锁最近已生效版本；
- 项目没有任何可用锁：任务开始仍被阻断。

因此“未来有新规则”不会让项目提前消费，也不会让项目在无知识快照状态下运行。

## 4. 项目状态模型

```
team-wiki project-status <project-root> <team-root>
```

状态包括：

- current：锁定版本就是最新已生效版本；
- update-available：存在已生效的新 Publication；
- deferred：review-required 更新已经显式 defer；
- scheduled：项目锁仍是最新已生效版本，但存在未来版本；
- unlocked：存在有效 Publication，但项目尚未锁定；
- scheduled-unlocked：只有未来版本且项目没有可用锁；
- no-publication：声明的知识尚无可消费 Publication。

如果同时存在：

```
v1 locked
v2 effective
v3 future
```

项目必须先处理 v2；v3 只作为 scheduled 信息显示，不能遮蔽已生效更新。

## 5. adoption_requirement 门禁

Publication 已定义三种要求，V0.7 将其转化为项目侧真实门禁：

### notice

- task start：允许；
- release：允许；
- 显示 warning；
- 项目可按自己的节奏升级 lock。

### review-required

- task start：允许，但 warning；
- release：阻断；
- 项目必须二选一：
  - accept：升级 lock；
  - defer：保留旧 lock，并给出理由。

Defer 只对精确的：

```
from_publication_id → to_publication_id
```

生效。后续出现新 Publication 时，旧 defer 不自动沿用。

### must-address

- task start：阻断；
- release：阻断；
- 不允许 defer；
- 必须 accept 并升级 lock。

命令：

```
team-wiki project-gate ... --phase start
team-wiki project-gate ... --phase release

team-wiki project-update ... K-A --decision accept --reason "..."
team-wiki project-update ... K-A --decision defer --reason "..."
```

Update decision 保存在：

```
.knowledge/records/update-decisions/UPD-*.yml
```

属于项目共享治理记录。

## 6. Task Knowledge Snapshot

任务开始：

```
team-wiki project-prepare <project-root> <team-root>
  --goal "实现订单导入"
```

会：

1. 执行 start gate；
2. 固定当前 `knowledge.lock` SHA；
3. 保存完整 lock snapshot；
4. 记录 project git 信息；
5. 创建本地 Project Work。

Work 位于：

```
.knowledge/runs/PW-*.yml
```

并保持本地，不要求提交。

## 7. 历史 Publication 精确读取

任务中不能直接读取 team-knowledge 当前工作树来替代锁版本。

```
team-wiki project-context <project-root> <team-root> <work-id> <knowledge-id>
```

会根据 Work snapshot 中的：

- published_ref；
- path；
- content_sha256；

执行 Git 历史读取并重新校验 hash。

因此：

```
任务锁定 v1
team repo 当前已经 v3
```

当前任务读取的仍然是 v1，而不是静默切到 v3。

## 8. 项目侧 Adopt / Observe

```
team-wiki project-adopt ...
team-wiki project-observe ...
```

只有真正影响任务产出的知识才记录 adopted。

Observe 继续使用统一结果：

- not-verified；
- supported-in-scope；
- boundary-found；
- contradicted；
- not-applicable。

这与团队侧 W/E/CHG 语义保持一致。

## 9. Task Finalize 与 Release Gate

```
team-wiki project-finalize <project-root> <team-root> <work-id>
```

执行顺序：

1. 检查当前 lock SHA 是否仍等于任务开始 snapshot；
2. 若 lock 中途改变，拒绝 finalize，要求新建 Work；
3. 执行 release gate；
4. 未处理的 review-required / must-address 阻断；
5. finalize Project Work；
6. 将正式 Publication adoption 回报 team-knowledge。

因此：

> task start 后升级 lock，不会让同一个 Work 混用两个知识版本。

## 10. Adoption 回报

Project finalize 使用 V0.6 的共享 Adoption Record：

```
team-knowledge/.knowledge/records/adoptions/ADOPT-*.yml
```

记录：

- consumer_id = project_id；
- project work ID；
- knowledge_id；
- publication_id；
- published_ref；
- used_for；
- outcome；
- evidence_ids。

Project Work 本身仍留在项目本地；只有具有团队复用价值的 adoption 结果进入 team-knowledge。

## 12. 端到端治理链

```
Team Publication
      ↓
Project explicit knowledge_ids
      ↓
knowledge.lock
      ↓
project-status / gate
      ↓
task prepare + lock snapshot
      ↓
historical exact context
      ↓
adopt / observe
      ↓
new Publication appears
      ↓
notice / review-required / must-address
      ↓
accept / defer / block
      ↓
release gate
      ↓
finalize
      ↓
team Adoption Record
```

## 13. 关键验收

V0.7 测试必须覆盖：

- 无 lock 时任务开始被阻断；
- review-required 更新允许开始但阻止 release；
- review-required 可有理由 defer；
- must-address 同时阻止 start/release；
- must-address 不允许 defer；
- accept 后 lock 精确升级到新 Publication；
- 历史 context 读取锁定 commit，而不是当前 team 工作树；
- 任务中途 lock 变化导致 finalize 失败；
- future Publication 不提前替换有效 lock；
- 已生效更新不能被更晚 scheduled Publication 遮蔽；
- Project finalize 生成团队 Adoption Record。

## 14. 当前边界

V0.7 暂不实现：

- 根据 scope/path/task 自动推断 knowledge_ids；
- 多个 team-knowledge 仓库联合 lock；
- 项目 CI 中自动调用 project-gate；
- GitHub branch protection 自动要求 project-gate；
- approved exception 对 must-address 的豁免机制；
- adoption requirement 的组织级 SLA；
- 自动升级项目 PR；
- 项目 lock 与远程 team repository 自动 fetch；
- 项目侧 Evidence 自动回流 CHG。

这些机制以后应在当前显式、可审查的 lock/gate 之上增加，而不是替代它。

## 15. 下一阶段

V0.8 优先考虑：

1. project-gate 接 GitHub CI / required check；
2. scope + task + path 的确定性适用规则选择；
3. approved exception 与到期机制；
4. team Publication → downstream project update proposal；
5. 项目侧 boundary/contradiction 自动回流原 CHG/Review；
6. 多 knowledge source 联合 lock。
