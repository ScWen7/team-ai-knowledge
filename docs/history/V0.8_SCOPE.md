# V0.8 落地范围：使用减负

V0.7 把团队知识接入业务项目消费流程后，工具能力已经够用，但**使用路径过长**。V0.8 不增加新的业务对象，只削减使用者在达成同样结果时必须显式经过的步骤。

核心判断：

> 负担的根源不是"层数多"，而是**同一套复杂度被原样暴露给了使用者**，
> 并且**部分记录没有任何下游消费者**。

因此本版本的原则是：

- 不删除任何已有命令和数据格式；
- 砍掉没有人消费的记录；
- 把"必须逐层声明"改成"必须显式说明关键项，其余取合理默认"；
- 语义判断一步都不自动化，仍由当前 Agent / 领域责任人明确。

---

## 1. 问题定位

在 V0.7 基线上，修改一条知识的最短路径为：

```text
ingest → intake-source → intake-status
  → intake-apply × N（每块一次，O(块数)）
  → candidate-create → patch-plan → patch-context → patch-apply
  → git commit → publish
```

以一份 3 万字文档（`max_chars=4000`，7 块）为例，至少 17 次命令调用。

项目侧同样存在固定顺序的手工拼接：README 用「工程师高频 5 命令」描述
`project-prepare → project-context → project-adopt → project-observe → project-finalize`，
这本身就说明使用者需要一个入口，而不是要记住顺序。

进一步核查发现三类**结构性问题**：

| 问题 | 证据 | 后果 |
|---|---|---|
| `review-progress` 无人消费 | `audit_intake` 只在 `cli.py` 被注册为命令，没有任何流程读取 `review_status` 作为前置条件 | 逐块填的账本不影响任何后续步骤 |
| `indexing` 状态永远为假 | `index_state` 仅在 `intake.py` 写入过一次 `"not-indexed"`，无任何代码写 `"indexed"`；代码中无 LanceDB 实现 | `source-status` 恒定输出一个无意义字段 |
| Candidate 无处可跳过 | `create_patch_plan` 直接调用 `candidate_context` 并要求已绑定证据，无旁路 | "改一段话"必须先理解 Candidate 对象 |
| 项目侧流程需手工排序 | 5 条命令必须严格按序调用，中间每步都要人工传递 `work_id` | 顺序记错即失败，且 README 不得不专门写一节 |

## 2. 优化一：`intake-decide`（O(块数) → O(1)）

新增命令，一次调用决定整份 intake：

```bash
team-wiki intake-decide <root> <intake_id> \
  --keep-evidence EVD-SRC-D82BE70E-...-0001 \
  --with-knowledge EVD-SRC-D82BE70E-...-0001:K-ORDER
```

行为：

- `--keep` / `--keep-evidence` 列出的块标记为 `integrated`；
- 其余块标记为 `skipped`，并自动填入默认理由；
- `--with-knowledge CHUNK:K-ID` 为指定块绑定目标知识；
- `--keep-all` 保留全部块，其余不改动；
- `--reset` 把所有块退回 `pending`。

不变的部分：

- 分块策略、`manifest.json`、`processing.yml` 完全不变；
- `review-progress.yml` 的账本结构不变；
- `intake-apply` 单块命令完整保留，供需要逐块精细控制时使用。

变化的是默认值方向：从"必须逐块声明"改为"**必须显式说明要保留哪些**"。

> 安全边界：不接受空的 `--keep`（也不接受 `--reset`）时直接报错，避免误将整份资料标记为无内容。

---

## 3. 优化二：移除 `indexing` 状态维度

`FINAL_DESIGN.md` §21.6 定义的来源处理阶段为：

```text
acquired → processed → evidence ready → indexed → compiled → published
```

其中 `indexed` 对应尚未实现的 LanceDB 派生检索层。实际代码中：

- `index_state` 只在生成 manifest 时写入一次 `"not-indexed"`；
- 没有任何代码路径会写入 `"indexed"`；
- 因此 `source_pipeline_status` 的 `indexing.state` **恒为 `not-indexed`**。

V0.8 的处理：

- `source_pipeline_status` 不再返回 `indexing` 段；
- `read_evidence` 不再返回 `index_state`；
- 新生成的 manifest 不再写入 `index_state` 字段。

来源处理在实现层面成为 4 个阶段：

```text
acquisition → processing → evidence → knowledge_change
```

这与 `FINAL_DESIGN.md` §21.6 的原始意图并不冲突——该节已声明"当前实现阶段可以缺失"。

> 若将来启用 LanceDB，应以**真实可写**的索引状态重新引入该维度，而不是先留一个恒假字段。

## 4. 优化三：`patch-plan-direct`（Candidate 降级为实现细节）

新增直连命令：

```bash
team-wiki patch-plan-direct <root> \
  --knowledge K-ORDER \
  --comparison narrows \
  --statement "订单导入必须幂等，且幂等键为订单号与业务线组合。" \
  --evidence EVD-SRC-...-0001 \
  --summary "收窄幂等适用范围"
```

内部行为与 `candidate-create` + `patch-plan` **完全一致**：

1. 生成同样的 `CAND-*.yml` 记录；
2. 同样调用 `bind_evidence` 建立 `supports` 绑定；
3. 同样调用 `create_patch_plan` 执行全部前置校验；
4. 同样产生 CHG / Review / 依赖影响记录。

因此**磁盘契约和所有下游门禁完全不变**，变的只是使用者不需要理解 Candidate 这个中间对象。

保留的强制约束：

- `comparison` 必须由调用方明确给出，**确定性代码不推断语义关系**；
- 必须提供 `--statement` 和至少一个 `--evidence`；
- 目标知识存在时沿用其 `id` / `title` / `type`；
- 目标不存在时要求 `comparison=new` 且必须提供 `--target-path`。

原有的 `candidate-create` / `patch-plan` / `candidate-show` 全部保留，供需要精细控制和审阅 Candidate 的场景使用。

## 5. 优化四：Candidate Batch 标记为实验性

`batch.py` 服务于"多个 Candidate 归并为一个"的场景，目前无已知真实使用。

处理方式：

- 代码保留、CLI 保留、测试保留；
- 模块 docstring 与本文件明确标注 EXPERIMENTAL；
- 移出主文档推荐路径；
- 单来源修改一律走 `patch-plan-direct`。

不做删除，是因为该模块逻辑独立、测试完整，保留成本仅为"不在主路径上宣传"。

## 6. `project-work`：项目侧 5 步收敛为 2 步

README 中长期存在的「工程师高频 5 命令」说明：使用者已经在**手工拼接固定顺序的流程**。V0.8 提供一个外观命令，把这条路径收敛为两次调用。

```bash
# 开始：start 门禁 → 锁定快照 → 直接返回锁定正文
team-wiki project-work ./proj <team-root> --phase start \
  --goal "实现订单导入" --read K-A

# 收尾：adopt + observe → release 门禁 → 回报团队
team-wiki project-work ./proj <team-root> --phase finish \
  --work-id <PW-...> \
  --adopt K-A --used-for "实现导入校验" \
  --observe "K-A:supported-in-scope:批量场景验证通过"
```

**这不是新的绕过路径。** `project-work` 只是依次调用既有函数，所有门禁照常执行：

- `--phase start` 内部调用 `project_gate(phase="start")` 与 `prepare_project_work`；
- `--phase finish` 内部调用 `project_adopt` / `project_observe` / `finalize_project_work`；
- `must-address` 仍然阻断 start，`review-required` 仍然阻断 release；
- 任务中途 lock 变化仍然拒绝 finalize。

已有的 5 条命令**全部保留**，需要分步执行或中途查看状态时照常使用。

安全边界：

- `--phase start` 必须提供 `--goal`；`--phase finish` 必须提供 `--work-id`；
- `phase="start"` **不会** finalize，因此不会为进行中的工作产生 adoption；
- 未先 adopt 就 observe 依然报错，前置约束未被放宽；
- `--used-for` 缺省时写入「未说明具体用途」，而不是静默留空。

## 7. `status`：把报告变成待决策工单

`doctor` 回答「结构是否合法」，`doctor --report stale` 回答「什么变冷清了」。
两者都没有回答维护者每天开工真正会问的那句：

> **现在有什么在等我？我该敲什么？**

`stale.py` 早就能算出三类信号，但它只输出一份需要人主动去读的报告。
V0.8 新增 `team-wiki status`，把这些已有信号汇总成**带原因和下一步命令**的决策项。

```bash
team-wiki status .
```

输出示例：

```text
# 待决策事项

## 阻塞中（1）

### [发布被阻塞] CHG-01ECE22F 确认订单导入边界

stage=proposed，但仍有 1 个未处理 Review（导入与退款规则冲突），发布会被拒绝。

team-wiki review-resolve . REV-2251E96ABB --action <action> --note "<理由>"
team-wiki publish . CHG-01ECE22F <knowledge-id> --requirement <...>

## 需要留意（1）

- **[资料积压未登记]** 5 份资料已投递但未登记
  - sources/inbox/ 中的文件不会自动成为知识。需要执行 ingest 登记为稳定 source。
  - 下一步：`team-wiki ingest . sources/inbox/note1.md --title "<标题>"`
```

### 决策项类型与严重级别

| kind | severity | 含义 | 触发条件 |
|---|---|---|---|
| `blocked-publish` | blocking | 变更无法发布 | CHG 处于 proposed/ready 且 Review 未处理 |
| `stale-review` | blocking / attention | Review 长期未处理 | open 超过阈值；正在阻塞发布时升级为 blocking |
| `zero-adoption` | attention | 发布后无人使用 | Publication 发布超过阈值且无任何 adoption |
| `stale-knowledge` | attention | active 知识长期未更新 | 超过阈值未修改 |
| `long-draft` | attention | draft 长期未推进 | draft 状态超过阈值 |
| `inbox-backlog` | attention | 资料积压未登记 | inbox 文件数超过阈值 |

### 边界

- **不新增任何状态，不修改仓库。** 有测试断言连续两次调用后文件清单完全一致。
- **不替代 `doctor`。** 结构合法性仍由 `doctor` 负责；`status` 只回答决策。
- **不自动修复。** 每一项只给出可执行命令，由人决定。
- 阈值全部可调：`--zero-adoption-days / --stale-active-days / --draft-days / --review-days / --inbox-limit`。

## 8. 检索修复：中文自然语言查询从 0% 恢复

这一项不属于减负，属于**修正失效的核心能力**，因此单独说明。

### 问题

原 `search` 只按空白切分查询：

```python
terms = [x.lower() for x in re.split(r"\s+", query.strip()) if x]
```

中文没有空白，于是一句自然语言提问被当成**一个词元**，再拿整串去做子串匹配：

```text
"手机号能不能为空" -> ['手机号能不能为空'] -> 正文匹配 0 次
```

而知识正文写的是「手机号为必填项」——语义完全对应，字符零重叠。

实测（4 条知识的库）：

| 查询 | 修复前 |
|---|---|
| 手机号能不能为空 | 0 条 |
| 重复导入会怎么样 | 0 条 |
| 多久可以退款 | 0 条 |
| 收货人电话要填吗 | 0 条 |
| 必填字段有哪些 | 0 条 |
| 错误码怎么处理 | 0 条 |
| **自然语言命中率** | **0 / 10** |

`context` 内部直接调用 `search`，因此 `direct` 与 `related` 同时为 0，整体失效。

**危险之处在于它不报错。** 返回空列表，Agent 会合理地推断「知识库里没有这条」，
然后按自身理解作答，而不是提示「知识缺失」。

### 修复

字符 n-gram，无需词典、分词模型或向量库：

- CJK 连续片段展开为 2-gram / 3-gram；
- 拉丁与数字保持整词，`CONTACT_PHONE_REQUIRED` 仍精确匹配；
- 标点作为分隔符剥离；
- 按字段加权（title 6 / tags 4 / summary 3 / body 1）；
- 长 n-gram 权重更高（`手机号` 比 `手机` 更有说服力）。

结果：

| 查询 | 修复前 | 修复后（Top 1） |
|---|---|---|
| 手机号能不能为空 | 0 条 | `RULE-CONTACT-PHONE` ✓ |
| 重复导入会怎么样 | 0 条 | `RULE-IDEMPOTENT` ✓ |
| 多久可以退款 | 0 条 | `RULE-REFUND-WINDOW` ✓ |
| 错误码怎么处理 | 0 条 | `DOC-ERROR-CODES` ✓ |
| 收货人电话要填吗 | 0 条 | `RULE-CONTACT-PHONE` ✓ |
| **自然语言命中率** | **0%** | **100%** |

负例仍然干净拒绝：

```text
今天天气怎么样 / 篮球比赛 / Kubernetes 部署 / zzzqqqxxx  -> 0 条
```

### 为什么不引入向量检索

字符 n-gram 已把中文自然语言命中率从 0% 恢复到 100%，且排序正确。
在**没有真实评测集**之前引入 LanceDB / embedding，只能增加依赖和不确定性，
却无法证明比现在更好。`FINAL_DESIGN.md` §16 原本就要求
「真实中文和团队任务验证有收益后再启用」——本次修复正好说明：

> 先让确定性的东西真正可用，再考虑不可确定的东西。

### 遗留边界

- 无同义词与语义泛化（"手机" vs "联系电话" 需靠字符重叠而非词典关联）；
- 无长文档分块检索，知识条目过长时相关性会下降；
- 仍是全量线性扫描，规模上千篇后需要索引层；
- 排序未做长度归一化，短文档在重复词上会略微占优——
  在没有真实评测集前不做调参，避免过拟合想象出来的场景。

以 3 万字文档（7 块）修改一条知识为例：

| | V0.7 | V0.8 |
|---|---|---|
| 修改一条知识的命令数 | 17 | **10** |

## 11. 关键验收

V0.8 测试必须覆盖：

- `intake-decide` 保留指定块、其余自动 skipped 且带理由；
- `intake-decide` 支持按 evidence_id 指定并绑定 knowledge_id；
- `intake-decide --reset` 退回 pending；
- 空的 `intake-decide` 报错；
- `intake-decide` 对未知 chunk 报错；
- `intake-audit` 在 decide 前 `complete=false`、之后 `complete=true`；
- `source-status` 在处理前后都不含 `indexing`；
- `read_evidence` 不含 `index_state`；
- manifest chunk 不持久化 `index_state`；
- `patch-plan-direct` 生成 Candidate 记录且绑定证据；
- `patch-plan-direct` 仍可 apply，并检测目标并发漂移为 stale；
- `patch-plan-direct` 拒绝空 evidence / 空 statement / 非法 comparison；
- `patch-plan-direct` 的 `patch-context` 输出完整。

`status` 必须覆盖：

- 空仓库报告「没有需要你决策的事项」；
- 新的 active 知识不被误报；
- proposed/ready 且有未处理 Review 的 CHG 判为 blocking；
- **处理掉 Review 后该阻塞项消失**；
- 阻塞项消失后 `publish` 确实可以成功（status 与 publish 必须一致）；
- `collecting` 阶段的 CHG 不算发布阻塞；
- 长期 open 的 Review 被报告，阻塞发布时升级为 blocking；
- 三类老化信号各自被报告且都带可执行命令；
- inbox 积压超过阈值才报告，且阈值可调；
- **每一项都带原因和下一步命令**；
- 输出 JSON 可序列化；
- **连续调用不修改仓库任何文件**。

检索必须覆盖：

- 分词把 CJK 展开为 n-gram，拉丁保持整词，标点被剥离；
- 空查询与纯标点查询返回空；
- **8 条自然语言提问必须命中，且 Top 1 正确**；
- 提问措辞与知识正文不同时仍能命中；
- 5 条无关提问必须返回 0 条（错误答案比没有答案更糟）；
- 空格分词、单词查询、拉丁标识符、混合中英文均未回归；
- 结果按分数降序、字段结构不变；
- `INDEX.md` 导航文件不得盖过真实知识；
- `context` 规划随之恢复，且仍声明 `complete=false`。

`project-work` 必须覆盖：

- start 创建 Work 并返回锁定正文，且**不** finalize、不产生 adoption；
- start 缺少 `--goal` 报错，finish 缺少 `--work-id` 报错，非法 phase 报错；
- finish 记录 adoption 并回报团队仓库；
- 未 adopt 就 observe 仍然报错；
- `must-address` 仍然阻断 start；
- `review-required` 仍然阻断 release；
- 任务中途 lock 变化仍然拒绝 finish；
- **外观命令与五条命令手工执行产生完全相同的 Work 状态**。

## 12. 当前边界

V0.8 仍不实现：

- 语义比较（`comparison`）的自动推断；
- 知识更新要求的自动推荐；
- CI 门禁接入；
- LanceDB / 向量检索；
- 自动从 PDF / Word 抽取文本（当前 `intake-source` 仅支持 UTF-8 文本与 Markdown）。

**当前最重要的下一步不是继续加功能，而是用真实资料跑通一次完整闭环，并据此决定 `batch` / `connector` / `scope` 是否标记为实验性。**
