# 成员使用指南

适用于产品、业务、运营、测试、工程等成员。你可以使用团队已有 Git Web 界面，或让当前 Agent 协助，无需理解内部记录和命令。

## 找到需要的知识

从团队库的知识导航进入；项目具体设计和踩坑通过项目入口进入对应项目文档库。搜索结果可以包含草稿或历史线索，使用前看清有效状态、适用条件和来源。

可以这样告诉 Agent：

> 查找这个项目有关依赖更新的经验，给出适用条件和原文位置；找不到或存在冲突时直接说明。

团队共同底线由项目配置和规则入口加载。参考资料的搜索排名不决定哪些底线可以省略。

## 提交资料或经验

- 已有项目设计、决策、踩坑：保存在项目原有文档位置，不另复制一份到团队库。
- 团队资料：按团队约定交到资料投递区，附一句用途和来源。
- 项目经验可能有跨项目价值：提出可复用的结论和适用条件，引用项目原文，由负责人审核是否进入团队域。

可以这样告诉 Agent：

> 将这次排查中可复用的结论整理到项目经验库，保留问题现象、原因、解决方法、适用条件和证据。不要把未经验证的推断写成事实。

PDF、Word 和图片可按仓库规则作为资料附件保存；当前工具不会自动读懂这些格式，需要先转换或人工摘取可核查内容。

## 发现错误或过期内容

在对应文档提出修改或让 Agent 准备差异，说明哪里有问题、依据是什么、影响哪些范围。负责人沿用现有 Git 审核渠道确认。

可以这样告诉 Agent：

> 这条知识与本项目实际情况不一致，请核对来源和适用范围，提出修订，不要直接覆盖成新的事实。

提交资料、格式整理和审核通过是不同状态。系统目前不自动分配负责人、不自动创建远端提醒，也不自动合并或发布。

## 首次接入已有项目

维护者或 Agent 先盘点文档并提供治理预览。自动整理只补齐确定的元信息，原正文、代码示例和导航保留。需要你判断的是归属、结论是否成立、冲突与适用范围，通常无需逐文件处理排版。

“待确认”表示信息不足，不代表文档没有价值。长期未修改或没有采用记录也不等于知识无效。

## 维护责任

项目原文由项目负责，团队结论由团队对应负责人负责。重要来源变化或新反例应反馈到权威文档；浏览和使用知识无需填写每次任务的采用记录。
