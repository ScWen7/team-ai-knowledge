# V0.8 落地范围：使用减负

V0.7 把团队知识接入业务项目消费流程后，工具能力已经够用，但**使用路径过长**。V0.8 不增加新的业务对象，只削减使用者在达成同样结果时必须显式经过的步骤。

核心判断：

> 负担的根源不是"层数多"，而是**同一套复杂度被原样暴露给了使用者**，
> 并且**部分记录没有任何下游消费者**。

因此本版本的原则是：

- 不删除任何已有命令和数据格式；
- 砍掉没有人消费的记录；
- 把"必须逐层声明"改成"必须显式说明关键项，其余取合理默认"；
- 语义判断一步都不自动化，仍由当前 Agent / 领域责任人明确。

---

## 1. 问题定位

在 V0.7 基线上，修改一条知识的最短路径为：

```text
ingest → intake-source → intake-status
  → intake-apply × N（每块一次，O(块数)）
  → candidate-create → patch-plan → patch-context → patch-apply
  → git commit → publish
```

以一份 3 万字文档（`max_chars=4000`，7 块）为例，至少 17 次命令调用。

进一步核查发现三类**结构性问题**：

| 问题 | 证据 | 后果 |
|---|---|---|
| `review-progress` 无人消费 | `audit_intake` 只在 `cli.py:145` 被调用，没有任何流程读取 `review_status` 作为前置条件 | 逐块填的账本不影响任何后续步骤 |
| `indexing` 状态永远为假 | `index_state` 仅在 `intake.py` 写入过一次 `"not-indexed"`，无任何代码写 `"indexed"`；代码中无 LanceDB 实现 | `source-status` 恒定输出一个无意义字段 |
| Candidate 无处可跳过 | `create_patch_plan` 直接调用 `candidate_context` 并要求已绑定证据，无旁路 | "改一段话"必须先理解 Candidate 对象 |

---

## 2. 优化一：`intake-decide`（O(块数) → O(1)）

新增命令，一次调用决定整份 intake：

```bash
team-wiki intake-decide <root> <intake_id> \
  --keep-evidence EVD-SRC-D82BE70E-...-0001 \
  --with-knowledge EVD-SRC-D82BE70E-...-0001:K-ORDER
```

行为：

- `--keep` / `--keep-evidence` 列出的块标记为 `integrated`；
- 其余块标记为 `skipped`，并自动填入默认理由；
- `--with-knowledge CHUNK:K-ID` 为指定块绑定目标知识；
- `--keep-all` 保留全部块，其余不改动；
- `--reset` 把所有块退回 `pending`。

不变的部分：

- 分块策略、`manifest.json`、`processing.yml` 完全不变；
- `review-progress.yml` 的账本结构不变；
- `intake-apply` 单块命令完整保留，供需要逐块精细控制时使用。

变化的是默认值方向：从"必须逐块声明"改为"**必须显式说明要保留哪些**"。

> 安全边界：不接受空的 `--keep`（也不接受 `--reset`）时直接报错，避免误将整份资料标记为无内容。

---

## 3. 优化二：移除 `indexing` 状态维度

`FINAL_DESIGN.md` §21.6 定义的来源处理阶段为：

```text
acquired → processed → evidence ready → indexed → compiled → published
```

其中 `indexed` 对应尚未实现的 LanceDB 派生检索层。实际代码中：

- `index_state` 只在生成 manifest 时写入一次 `"not-indexed"`；
- 没有任何代码路径会写入 `"indexed"`；
- 因此 `source_pipeline_status` 的 `indexing.state` **恒为 `not-indexed`**。

V0.8 的处理：

- `source_pipeline_status` 不再返回 `indexing` 段；
- `read_evidence` 不再返回 `index_state`；
- 新生成的 manifest 不再写入 `index_state` 字段。

来源处理在实现层面成为 4 个阶段：

```text
acquisition → processing → evidence → knowledge_change
```

这与 `FINAL_DESIGN.md` §21.6 的原始意图并不冲突——该节已声明"当前实现阶段可以缺失"。

> 若将来启用 LanceDB，应以**真实可写**的索引状态重新引入该维度，而不是先留一个恒假字段。

## 4. 优化三：`patch-plan-direct`（Candidate 降级为实现细节）

新增直连命令：

```bash
team-wiki patch-plan-direct <root> \
  --knowledge K-ORDER \
  --comparison narrows \
  --statement "订单导入必须幂等，且幂等键为订单号与业务线组合。" \
  --evidence EVD-SRC-...-0001 \
  --summary "收窄幂等适用范围"
```

内部行为与 `candidate-create` + `patch-plan` **完全一致**：

1. 生成同样的 `CAND-*.yml` 记录；
2. 同样调用 `bind_evidence` 建立 `supports` 绑定；
3. 同样调用 `create_patch_plan` 执行全部前置校验；
4. 同样产生 CHG / Review / 依赖影响记录。

因此**磁盘契约和所有下游门禁完全不变**，变的只是使用者不需要理解 Candidate 这个中间对象。

保留的强制约束：

- `comparison` 必须由调用方明确给出，**确定性代码不推断语义关系**；
- 必须提供 `--statement` 和至少一个 `--evidence`；
- 目标知识存在时沿用其 `id` / `title` / `type`；
- 目标不存在时要求 `comparison=new` 且必须提供 `--target-path`。

原有的 `candidate-create` / `patch-plan` / `candidate-show` 全部保留，供需要精细控制和审阅 Candidate 的场景使用。

## 5. 优化四：Candidate Batch 标记为实验性

`batch.py` 服务于"多个 Candidate 归并为一个"的场景，目前无已知真实使用。

处理方式：

- 代码保留、CLI 保留、测试保留；
- 模块 docstring 与本文件明确标注 EXPERIMENTAL；
- 移出主文档推荐路径；
- 单来源修改一律走 `patch-plan-direct`。

不做删除，是因为该模块逻辑独立、测试完整，保留成本仅为"不在主路径上宣传"。

## 6. 顺带修复

- **macOS 临时目录 symlink 崩溃**：`apply_patch_plan` 在 `/var` → `/private/var` 环境下
  对 `relative_to` 失败，导致 `test_v05` / `test_v06` 报错。现统一经 `_repo_relative()` 计算仓库相对路径。

## 7. 效果

以 3 万字文档（7 块）修改一条知识为例：

| | V0.7 | V0.8 |
|---|---|---|
| 命令调用数 | 17 | **10** |
| 逐块声明次数 | 7 | **0** |
| 需要理解的对象 | Candidate / Batch / Plan / Intake / Review / CHG | **Plan / CHG**（其余为实现细节） |
| `source-status` 假字段 | 1 | **0** |

V0.8 命令总数为 56（原 54 + `intake-decide` + `patch-plan-direct`），但**高频路径的命令数下降**，低频能力完整保留。

## 8. 关键验收

V0.8 测试必须覆盖：

- `intake-decide` 保留指定块、其余自动 skipped 且带理由；
- `intake-decide` 支持按 evidence_id 指定并绑定 knowledge_id；
- `intake-decide --reset` 退回 pending；
- 空的 `intake-decide` 报错；
- `intake-decide` 对未知 chunk 报错；
- `intake-audit` 在 decide 前 `complete=false`、之后 `complete=true`；
- `source-status` 在处理前后都不含 `indexing`；
- `read_evidence` 不含 `index_state`；
- manifest chunk 不持久化 `index_state`；
- `patch-plan-direct` 生成 Candidate 记录且绑定证据；
- `patch-plan-direct` 仍可 apply，并检测目标并发漂移为 stale；
- `patch-plan-direct` 拒绝空 evidence / 空 statement / 非法 comparison；
- `patch-plan-direct` 的 `patch-context` 输出完整。

---

## 9. 当前边界

V0.8 仍不实现：

- 语义比较（`comparison`）的自动推断；
- 知识更新要求的自动推荐；
- CI 门禁接入；
- LanceDB / 向量检索；
- 自动从 PDF / Word 抽取文本（当前 `intake-source` 仅支持 UTF-8 文本与 Markdown）；
- 项目侧 `project-work` 聚合命令。

**当前最重要的下一步不是继续加功能，而是用真实资料跑通一次完整闭环，并据此决定 `batch` / `connector` / `scope` 是否标记为实验性。**
