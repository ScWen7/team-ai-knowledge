# 团队与项目知识库：稳定契约

状态：现行。实现与验证边界见 `README.md`、`VALIDATION.md`。V0.1—V0.9 范围文档仅用于历史追溯。

## 1. 目标

1. **AI 开发标准化**：不同成员、不同 Agent 按同一组共同底线交付。
2. **知识不依赖个人和聊天**：事实、决策和经验有持久位置、来源和适用条件，并能被纠正。
3. **低成本维护**：非技术成员能查找、提交、纠错；维护者不手工同步状态。
4. **规模下仍准确、高效**：能识别权威、范围、冲突与失效，检索质量有数据。

## 2. 稳定层：文件契约

这一层是数据格式，不依赖任何工具实现。**只有出现真实事故或失败用例时才允许修改。**

- 知识是 Git 中的 Markdown，可带 frontmatter。文档与 Git 是唯一事实来源，不维护数据库或持久缓存。
- 团队库与项目库是两个仓库。同一结论只有一个权威位置；项目经验上提团队库时须提炼适用条件并引用项目来源。
- 推荐字段：`id`、`title`、`type`（`rule` 团队约定 / `tech` 技术 / `biz` 业务 / `project` 项目）、`status`、`scope`、`owner`、`summary`、`source`、`verified_at`。缺失字段只报告，不猜测；格式整理不把 draft 变成 active，不把最后提交人当负责人。
- 项目按 `repository_id + knowledge_ids + 锁定 commit/hash` 订阅团队底线。
- 变更只走 Git 审核（PR）。合并不等于所有项目已采用。

## 3. 四类知识的处理差异

| type | 特点 | 读取方式 | 必备信息 |
|---|---|---|---|
| rule 团队约定 | 数量少，强制 | 订阅后完整读取，不经 Top-K | 版本、生效条件、团队负责人审核 |
| tech 技术 | 有版本和环境边界 | 按任务检索 | 适用版本/环境、证据 |
| biz 业务 | 会随业务变化 | 按任务检索 | owner、source、verified_at |
| project 项目 | 随项目生灭 | 留在项目仓库，按任务检索 | 项目内位置即权威 |

## 4. 可替换层：接口

以下接口固定，实现可替换而不改变文件契约。

- **检索**：`search(query, scope, status) → [{id, path, status, title, score}] + issues`。单个文件损坏或 ID 重复时跳过并报告，不整体失败。
- **规则读取**：`project-rules` 完整返回所订阅底线的锁定正文，并核对版本与内容一致。
- **Agent 入口**：`agent-entry` 向 `AGENTS.md` 写入带标记的约定块——开工读规则并先搜索，收工判断是否沉淀，检索失败时追加评测用例。
- **评测**：`.knowledge/eval.yml` 保存真实问题与期望文档，`eval` 输出 recall@k、MRR 和负例通过数。
- **校验**：`doctor`、`govern` 检查结构、重复 ID、断链和待确认字段，可作为 CI 检查。

## 5. 复利机制

复利来自三个动作，而不是记录本身：

1. **收工沉淀**：Agent 收工时判断是否产生可复用的决策、踩坑或修正，写入原位置并随代码审核。
2. **上提与反例**：跨项目有价值的结论提炼后 PR 到团队库；项目发现反例时向团队库提修改。
3. **评测积累**：每次检索遗漏或误命中追加为评测用例。用例集是检索质量的长期依据。

无采用记录只表示未观测；久未修改只是复核线索，不能判定失效。

## 6. 规模与升级触发

现在不做的事，及触发它的条件：

| 升级项 | 触发条件 |
|---|---|
| 排序改进（长度归一化、泛词阈值） | 评测显示正确文档排名靠后或负例误命中——**已触发**，见 `VALIDATION.md` |
| 可丢弃的本地索引（不入库、不作为事实来源） | 文档数超过约 2000，或单次查询超过约 1 秒 |
| 向量检索 | 评测集 recall@5 达不到目标，且排序调优无效 |
| 迁入平台型系统（如 WeKnora） | 需要多租户权限，或大量非 Git 用户批量使用；知识仍是 Markdown，可作为数据源导入 |
| 目录 INDEX 分层 | 单目录文档数使人工与 Agent 浏览不可行 |

## 7. 协作

- 非技术成员通过 Git Web 或当前 Agent 浏览、提交资料、指出错误。
- 审核沿用 CODEOWNERS 与 PR；工具不自建通知、负责人分配或发布系统。
- 项目文档的权威与规则由项目负责，团队结论由团队对应负责人负责。

## 8. 冻结与验收

- 已实现但不再扩展的历史协议（CHG、Publication、Adoption、Evidence、Candidate、Connector、Intake、Work 流程）保持兼容，不新增功能；试点后按实际使用决定删除。
- 工程验收：治理安全与幂等、原目录可检索、完整底线读取、坏文件不阻塞检索、检索不写文件、评测可复现。
- 产品试点须证明：成员找到适用项目资产并识别权威来源；项目真实工作留下可复用记录；一项经验经提炼进入团队域并被其他项目复用；非技术成员完成一次贡献。
- 合成或样本评测不证明真实团队语义命中率。
