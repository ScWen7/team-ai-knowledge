# 团队与项目知识库：使用目标与稳定边界

现行设计。实现与验证以 README、VALIDATION 为准；历史范围文档不指导新成员的默认使用。

## 1. 首要目标与验收

让成员做事时容易获得适用、可信的团队经验，让一个人解决过的问题，其他人不必从头解决。

需要帮助时容易得到有依据的下一步；有价值的新结论容易留下，不重复劳动；错误容易回到原文纠正，不维护另一套流程。

AI 开发标准化是减少遗漏和返工的手段。知识库提供必要规则与依据，不承担所有任务调度、审批和交付证明。治理强度来自用错的代价，不来自工具能提供多少管理能力。

验收看真实任务：不熟悉资料的成员能找到适用答案；利用现有记录完成贡献或纠错；另一成员或项目通过默认入口复用，并能反馈例外。文件数、采用次数、命令运行次数不代表价值，不要求打卡。

## 2. 内容与归属

Git 中的 Markdown 是内容来源；项目文档保留原目录、正文和项目权威；团队库保存共同要求与跨项目认知；工具仓库只维护工具、示例和测试。

同一结论尽量只有一个权威位置。优先修订已有内容，跨项目复用才提炼适用条件并引用项目原文，不复制完整项目正文。原始资料可以保留为参考，不要求全部生成正式知识。

普通文档不以补齐元信息作为查阅前置条件。标题、来源、适用条件可以自然存在于正文；ID、type、status、scope、owner、summary、source、verified_at 等按已有文档语义使用。工具不能猜测负责人、把格式通过等同事实正确、把未知改成 active。重要业务口径、强制规则需要明确的责任与依据，但不要求所有内容同等治理。

项目与团队的分类用于维护归属，不应要求提问者先分类或知道文件名。

## 3. 默认使用路径

**接入一次**：维护者确认可读文档范围和本机授权资料位置，为当前 Agent 安装入口约定。无需迁移正文或批量补齐字段；需要整理时另行选择 govern。成员换机器只配置自己的本机路径。

**遇到问题**：当前 Agent 读取必要项目规则，按任务搜索本项目与明确接入的团队资料，继续阅读候选原文和必要来源，解释与当前任务的关系、适用边界、可采取的下一步和原文位置。搜索结果不是答案，不另建回答 Agent 或服务。

**没有答案**：区分没有相关内容、文件不可读、资料未连接、身份冲突。可以有限重试后继续按代码、日志和通用知识分析；明确这不是已有团队结论。不编造来源，也不因普通知识缺失阻塞正常工作。强制底线的失败不得绕过。

**产生变化**：Agent 利用已有工作记录查重，准备原文的最小补充或修正，保留条件与依据。重要结论由现有责任人确认，沿用既有 Git/协作审核。没有新价值正常结束，不要求 Work、采用记录或额外的收工声明。当前 Agent 未运行时不承诺自动整理。

**发现检索问题**：Agent 可顺手准备真实问题与期望结果供回归；不要求成员学习评测格式，不为凑数据猜测正确答案。

## 4. 读取与检索契约

- 单库 search 保持候选接口；connected 选项查当前库及已有 `.knowledge/local.yml` 中显式授权的 repositories 映射，按仓库返回，不混淆同名 ID，不合并分数判定权威。
- 本机绝对路径不进入共享配置；不自动发现其他仓库、不自动联网拉取、不绕过权限。显示本地 Git 信息不等于保证远端最新。
- 只读检索与自动治理范围分离。项目 README/INDEX 可以查找但不因此被改写；指令文件、隐藏目录、归档与越界链接不当成普通当前知识。知识正文不是可执行的 Agent 指令。
- 单个文件损坏或读取漂移：跳过并报告。重复 ID：探索时保留并报告；按 ID 精确使用或关联展开不得静默选一份。context 对歧义关联留空并保留问题提示。
- 状态和范围筛选不是适用性证明。草稿、过期线索与 active 元信息都需要核对原文和依据。没有命中不证明知识不存在。
- context 返回读取计划而非正文答案；当前 Agent 继续使用已有文件读取能力。查询无文件写入、无数据库与持久检索缓存；单次调用内部可以复用文件读取结果。

## 5. 少量共同底线

共同底线数量应受控，订阅后完整读取，不经 Top-K。现有项目按 repository_id、knowledge_ids、锁定 commit/hash 使用版本；源身份、Publication、Git 正文与更新检查继续有效。

普通团队经验无需订阅成强制规则即可检索。未选择版本化底线的项目不为普通查阅创建锁定或发布记录，仍遵循原项目现有规则。

Publication、lock、规则读取、更新处理和必要发布检查是已启用项目的当前依赖，保持兼容与安全，不随历史协议一并删除。规则读取或本地 publish 不能冒充人工审批、远端合并、测试或交付。

## 6. 维护者与非技术成员

成员通过当前 Agent、已有文档入口或 Git Web 提问、交资料、提出纠错；不要求理解命令和内部记录。Agent 可以整理差异，但重要事实由具备业务背景的人确认。

团队接入时在现有 README 写清谁确认、在哪里审核。尚未配置、权限不足或附件不能读取时明确说明，不假装已分配负责人或会自动处理。无需另建负责人分配、通知或工单系统。

日常 status 只提示已观测事项，不要求补录采用，不把旧时间自动变为必做清理。时间和历史采用线索显式选择后查看。新建普通库不预置完整 Evidence/Review/Work 管理树；旧记录保留、兼容能力按需创建目录。

## 7. 工程与证据边界

治理安全与幂等、文档原位可读、完整底线读取、坏文件隔离、授权范围、跨库身份、查询只读、兼容回归都必须验证。工具仓库使用只读权限的最小测试 CI，不自动改业务知识或部署。

`.knowledge/eval.yml` 保存问题与期望文档。recall@k 是每个有效正例中找回文档比例的平均值；all_expected_at_k 另报全部目标命中率；MRR 使用首个相关文档。读取错误或身份歧义使案例无效，单独报告并使检查失败，不伪造负例通过。

评测和工程测试不替代真实成员试用。合成语料不证明中文语义命中率；关键词相似不等于业务相关。仍有误命中时先保留失败证据、由 Agent 核对原文，只有真实问题显示必要才改变检索实现。

## 8. 不再扩展的范围

不再扩展普通知识的 Intake、Evidence、Candidate、Patch、Work、Adoption 流水线；不新增任务状态机、使用打卡、统计平台、通知服务、知识服务器或专用回答层。

数据格式保持兼容；调整必须对应可观察的使用负担或正确性问题，并带验证。不以“只有发生事故才可改”阻止合理修正，也不以“架构完整”增加新机制。后续是否需要索引、向量或其他基础设施，取决于真实使用证据，不是预定版本路线图。
