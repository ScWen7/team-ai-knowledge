# V0.5 落地范围：Evidence → Knowledge Patch Plan + Git Connector

V0.5 首次把“证据如何安全改变 Wiki”与“项目资料如何持续进入 Sources”两条链路跑通。

## 1. Evidence → Candidate → Patch Plan

### 1.1 Candidate Knowledge

新增 `Candidate` 记录，但它不是第五种正式业务对象，而是 CHG 形成前的工作产物：

```
.knowledge/records/candidates/CAND-*.yml
```

由当前 Agent / 领域责任人明确提供：

- proposed knowledge ID；
- title；
- knowledge type；
- statement；
- owner / scope。

程序不自行从 Evidence 猜业务结论。

Evidence 通过现有 `evidence-bind` 绑定 Candidate：

- supports；
- limits；
- contradicts；
- relevant。

Candidate 可以绑定多份 Evidence。

### 1.2 Candidate 与已有知识的比较

V0.5 使用显式 comparison：

- `new`：新的独立知识；
- `adds`：补充已有知识；
- `narrows`：收窄/增加适用条件；
- `contradicts`：与已有知识冲突；
- `duplicates`：重复，不修改。

这是 Agent/责任方的语义判断，程序只校验目标、证据和版本。

### 1.3 Knowledge Patch Plan

`patch-plan` 记录：

- Candidate；
- comparison / action；
- target knowledge ID/path；
- target base SHA256；
- Evidence IDs / bindings / Evidence SHA256；
- source revisions；
- change_id；
- 必要时的 review_id。

动作映射：

```
new         → create
adds        → update
narrows     → update
contradicts → review
duplicates  → no-change
```

除 `duplicates` 外，会进入现有 CHG；`contradicts` 还会创建/复用 contradiction Review。

### 1.4 安全应用 Agent 生成的正文

`patch-context` 返回：

- Candidate；
- 当前 Evidence；
- 原知识正文；
- Patch Plan；
- stale 状态。

当前 Agent 根据这些内容生成**完整 Markdown 修订稿**。

`patch-apply` 只负责确定性落盘：

1. 检查目标知识仍等于 Plan 的 base SHA；
2. 检查所有 Evidence 仍等于 Plan 记录的 Evidence SHA；
3. 校验 Markdown frontmatter ID；
4. create/update 目标文件；
5. 将 Plan 标为 applied；
6. 将 CHG 推进到 proposed；
7. 不自动发布。

如果知识或 Evidence 在 Plan 创建后变化，旧 Plan 必须失败并重新比较。

## 2. Local Git / Project Connector

### 2.1 Connector 配置

新增共享 Connector 记录：

```
.knowledge/records/connectors/<connector-id>.yml
```

记录：

- connector type = git；
- repository_id；
- include_paths；
- logical_root；
- auto_intake；
- checkpoint commit；
- tracked path → source_id；
- retired path → source_id。

**绝对本地仓库路径不写入共享配置。** 每次同步由调用者提供已授权的本地 checkout 路径。

### 2.2 初次同步

首次同步：

```
HEAD
 → git ls-tree(受控 include_paths)
 → 每个文件建立稳定 Source
 → tracked path → source_id
 → 可选 Text/Markdown intake
 → checkpoint = HEAD
```

Source upstream identity 使用：

```
connector_id + repository_id:path
```

### 2.3 增量同步

后续使用：

```
git diff --name-status -M old_checkpoint..HEAD
```

区分：

- add；
- modify；
- rename；
- delete。

rename 通过 connector 的 tracked mapping 保留原 `source_id`，只更新 upstream path / logical path 和 origin history。

modify 保持 source identity，产生新的 source revision。

delete 不删除本地 Source 或证据；标记 `deleted-upstream`。只有已经影响正式知识时，才创建 CHG/Review。

### 2.4 Checkpoint 安全

每次同步生成：

```
.knowledge/records/connector-runs/SYNC-*.yml
```

包含：

- from/to checkpoint；
- detected events；
- processed events；
- state；
- error；
- counts。

只有全部事件处理完成才更新 Connector checkpoint 和 tracked mapping。

失败时：

- sync run 标为 failed；
- checkpoint 不推进；
- 下一次从旧 checkpoint 重新计算；
- Source 的 add/refresh/delete 操作设计为可重复执行，避免重试制造重复版本。

### 2.5 删除判断边界

Git Connector 只有在 Git diff 明确返回 `D` 时，才把来源标记为 deleted-upstream。

以下情况不能解释成删除：

- 本次没有扫描到；
- include scope 改变；
- 本地 checkout 不完整；
- checkpoint 不可读取；
- Git 命令失败。

## 4. 关键验收

### Patch Plan

- Evidence 为空不能创建 Plan；
- target knowledge base hash 被锁定；
- Evidence current hash 被锁定；
- target 并发变化后 apply 失败；
- Evidence correction 后 apply 失败；
- apply 后只进入 proposed，不声称 published。

### Git Connector

- 首次同步建立 checkpoint；
- rename 保持 source_id；
- modify 保持 source_id 并增加 revision；
- delete 标记来源而不删除历史；
- 无知识依赖的来源变化不制造 CHG；
- 再次同步相同 HEAD 返回 no-change；
- checkpoint 只在整批成功后推进。
